# Product Selection Agent 参赛总报告

官方 Product Selection 题目 · 四人执行计划 · Amazon ESCI 数据分析 · SOTA 方法取舍

版本：2026-09-11。本文为团队统一执行版本，以最新提供的官方Product Selection描述为准，整合四人分工、数据研究与参赛策略。内容独立于任何已有软件项目。

**一页决策摘要**

项目定位：**帮助网店顾客理解商品信息、比较技术规格并选出适合自身需求的商品；Agent 会搜索、查证、按需澄清和重新选择，必要时将完整上下文交接给销售人员。**

团队已提供官方 Product Selection 的完整描述：顾客难以从分散的商品页面与复杂技术规格中选择适合的产品，导致放弃购买或求助销售，增加销售工作量并影响转化。以此作为全部业务需求，不再等待额外题目；数值评分权重仍未提供。

| 决策项 | 本次统一选择 |
|---|---|
| 面向谁、解决什么 | 网店顾客为主要用户，销售人员为交接接收者；把跨页查找与规格理解转成可确认的选择 |
| 第一版业务范围 | 首选笔记本电脑；先核验屏幕、内存、存储、处理器、接口等属性，范围由数据可用性控制 |
| 数据 | 英文 ESCI；完整 small 作为技术评测范围，应用目录按同类商品和证据完整度确定，不预设商品数量 |
| 架构 | 一个有状态 LLM Agent，调用搜索、查看商品、验证、生成选型单、保存交接草稿五种工具 |
| 搜索与重排 | BM25 Top-100 → 现成 Qwen3-Reranker-0.6B → Top-20；参数依资源试跑调整 |
| 关系与约束 | 对约 10 个最终候选判定 E/S/C/I；属性逐项判定满足、违反、未知，明确硬冲突不能被总分抵消 |
| 澄清 | 先查候选，只问能改变选择的问题；初始最多 2 轮，属于产品预算 |
| 最终交付 | 顾客可理解的 Top-3 条件对比、选择入口、选型结果；不能确认时给出交接草稿 |

| 人工评价规模 | 先做 60 会话：20 开发、40 测试；有余力增至 120：40 开发、80 测试 |
| 首版暂缓 | 专项微调、RL、多 Agent、复杂检索融合、多语言、支付及实时价格库存接入 |

**汇报时的三句话**

1. 网店顾客需要反复打开商品页、理解技术规格，仍难确认哪款适合自己。
2. Agent 汇集商品页信息，用用户能理解的方式比较差异，核验需求并引导选择。
3. 用公开排序基准、冻结的约束会话集和可观察的操作时间分别证明技术质量、决策可靠性与工作价值。

**官方题目与业务解释**

团队提供的完整原文：

> Customers visiting an online store often struggle to identify products that best meet their needs because product information is spread across multiple pages and technical specifications are difficult to compare. Many customers leave without purchasing or contact the sales team for assistance, increasing the workload of sales representatives and reducing online conversion rates.

据此，主用户明确为访问网店的顾客；销售人员是受益方和升级处理者。原型必须实际解决信息汇总和规格比较，不能只交付一个对话框或内部销售工具。推荐主流程是：顾客表达用途 → 搜索相关商品 → 读取候选详情 → 用统一属性比较 → 必要澄清 → 选择商品或带上下文咨询销售。

| 题目中的问题 | 产品响应 | 可观测结果 |
|---|---|---|
| 信息分散在多个页面 | 每个商品保留详情页，Agent 读取其证据并汇总对比 | 顾客完成任务所需打开的详情页数量 |
| 技术规格难比较 | 标准化单位、解释规格与需求的关系、展示差异 | 比较任务正确率、漏判明确条件数 |
| 顾客难以选到合适产品 | 按需求验证、澄清、替代和反馈重选 | 可接受选择率、完成时间、是否完成选择 |
| 销售答疑工作量高 | 顾客自助流程，必要时产生完整交接摘要 | 测试任务中的人工求助率及重复说明次数 |
| 在线转化率降低 | 增加可理解、可验证的选择路径及商品详情入口 | 原型只测选择/点击意向；真实购买转化留待线上试点 |

官网强调 SME 实际需求、可试点部署、Agent 的有效应用及业务价值；开发期截至 9 月 25 日、提交为 9 月 28 日、决赛为 10 月 10 日。数值评分权重未公布，不自行分配“官方占分”。[赛事页面](https://www.iss.nus.edu.sg/show-me-your-agents)

公开 ESCI 目录用于技术验证和网店原型，不代表实际企业目录或真实交易。无需等待企业材料才能开工；原型中明确标识数据快照，事实依据来自该快照，而非声称实时抓取 Amazon。

**四人分工：按可独立交付的模块划分**

使用 A/B/C/D 指代四位成员，直接分配名字即可。假设四人持续参与，技术偏好未知；默认把后端整合最强的人安排为 C，数据处理较强的人为 A，检索/模型经验较强的人为 B，前端与部署较强的人为 D。角色是人员职责，不代表四个运行时 Agent。

| 成员 | 主责与对外承诺 | 独立交付物 | 不负责的边界 |
|---|---|---|---|
| A：数据与评价负责人 | 提供干净目录、稳定 ID、证据数据、冻结评价与可信结果 | 目录快照、属性字典、数据 manifest、开发/测试清单、评测命令、结果页 | 不调对话策略；不把答案卡或 ESCI 标签放进应用目录 |
| B：检索与商品判断负责人 | 给定当前需求，返回候选、关系预测及条件验证结果 | BM25、reranker 适配、商品检查、三态验证、对比行与证据引用 | 不直接问用户；不决定放宽硬条件；不持有会话全局状态 |
| C：Agent 与后端整合负责人 | 从用户输入推进完整选择任务，确保状态和工具编排正确 | 会话服务、需求解析、工具循环、澄清、反馈更新、选型与交接结构化结果 | 不重复建立检索索引；不把 UI 文案写死进排序器 |
| D：顾客体验与交付负责人 | 把结果做成可现场使用的网店体验，并部署、记录和展示 | 浏览/详情页、聊天入口、商品卡、对比表、证据展开、选型单、部署和演示 | 不在前端重算商品分数或更改硬约束结论 |

共同责任：每人参加案例标注、每日联调与演示排练。C 为唯一集成负责人，A 为指标与数据划分负责人，D 为部署/提交负责人，B 为相关性与属性质量负责人；验收不过关时各负责人修复自己的模块，避免问题无人承接。

**每个人的任务清单与验收标准**

| 成员 | 必做任务 | 验收方式 |
|---|---|---|
| A | 冻结原始文件与 hash；按 locale+ID 连接；筛同类商品；统一单位与证据 ID；拆出无标签应用目录；准备 20 开发+40 测试会话；实现指标和报告 | 全部目录 ID 唯一；所有证据能定位原文；开发/测试按原 query 隔离；应用导出无 qrels；统计可一键重算 |
| B | 标题/卖点 BM25；冻结 reranker；按条件选相关证据；输出 E/S/C/I 预测；验证明确数值/型号/接口；缺失保留 unknown；生成属性差异 | 同样输入能复现检索路径；不出现目录外商品；硬反证被标为违反；否定/单位/缺失专项案例通过；给出延迟与基线差值 |
| C | 模型调用统一入口；结构化需求；会话版本；五种工具注册；状态驱动提问；允许替代的条件变更；超时/空结果恢复；返回前后端合同 | 完整需求不强制提问；已回答属性不重复问；用户撤回/更改条件立即生效；最多 2 轮澄清初始预算；超时或无结果有可执行下一步 |
| D | 原型店铺列表/详情；需求对话；Top-3 卡与最多3商品比较；证据引用；“选择此商品”“咨询销售”；部署配置、事件日志与录屏；有余力再做P1下载 | 新浏览器能完成三条演示；未知属性不显示为已满足；刷新可恢复会话；错误状态可理解；选择/比较/求助事件可回放 |

标注安排：每人独立起草 15 个会话（5 开发、10 测试），共60个；A↔D、B↔C交叉复核，争议由 A 组织按原文证据裁决。A 管理冻结清单；模型与提示词调优只看开发集。测试集制作阶段接触过的内容不可当作“从未见过的盲测”，报告如实说明为内部冻结集；可以另留少量由未参与调优者提出的新需求做现场检验。

**产品范围与第一天的品类决策**

主场景选“按用途选笔记本电脑”：顾客能描述办公、学习、便携等目标，但不一定理解内存、存储和接口差别。这与题目中的技术规格比较直接相关，ESCI 已检查到真实的复合笔记本需求。数量与字段覆盖需现场扫描，不能因为少量样例就假定目录充分。

A 在第一天抽查至少50个初筛条目，报告商品/配件区分、关键字段缺失与相互冲突。内部选类门槛建议：能建立至少200个同类商品条目，且抽查中至少80%有屏幕、内存、存储三项中的两项可定位证据；这些是开工门槛，不是已达到的统计。若不满足，24小时内切换为键盘/鼠标等属性更容易验证的单一类别，不为多品类重做框架。

笔记本首版属性为品牌、型号/系列、屏幕尺寸、RAM、存储容量/类型、处理器型号、接口；重量有证据才使用。原始型号或容量不能被当成经过实测的性能、续航或游戏帧率。用途偏好可以帮助排序，但“能流畅运行某软件”等结论必须有证据或保留不确定。价格、库存和配送不纳入自动满足承诺。

| 优先级 | 功能 | 截止前取舍 |
|---|---|---|
| P0 | 搜索并读取真实目录、统一规格对比、证据核验、按需澄清、反馈重选、明确选择或交接、可部署演示、核心评价 | 必须交付 |
| P1 | 下载选型单、指标可视化、英文之外的交互语言、更丰富的筛选器 | P0通过后按剩余时间做；交接摘要和屏幕结果仍属P0 |
| P2 | 微调、dense融合、RL、多Agent、多品类、实时库存价格、购物车支付 | 提交后路线图 |

**接口先定，四个人从第一天同时开工**

采用一个后端和模块化工具函数，避免为了分工拆出多个服务。C 维护共享类型与API定义，变更需通知所有使用者；A/B/D用固定示例实现并行开发。以下是设计合同，尚未实现。

| 合同 | 提供者→使用者 | 必须包含 |
|---|---|---|
| CatalogSnapshot | A→B/C/D | catalog_version、product_key=locale:product_id、title、原始字段、标准化属性、证据列表、原始数据来源 |
| RequirementState | C→B/D | session_id、state_version、原query、用途、条件列表、hard/soft、来源原话、已问问题、用户明确放宽记录 |
| CandidateSet | B→C | catalog_version、state_version、candidate_set_id、商品ID、检索/重排分数、关系预测、每项条件判定及证据ID |
| AgentResponse | C→D | session_id、state_version、action、message、question、recommendations、comparison、handoff、工具动作摘要 |
| EvalRecord | A制定；B/C/D产生 | case_id、版本、输出ID、动作序列、用量与耗时、失败类型；真值留在评价端 |

属性证据记录 `{evidence_id, product_key, field, quote, normalized_value}`。字段引用或quote能定位到快照原文，证明依据存在；quote存在本身不证明推理正确，语义判定仍需人工抽查。关系类别允许 uncertain，缺失证据不能被强制四分法掩盖。

后端最小HTTP接口：创建会话；提交一轮用户消息；读取商品详情；取回会话结果；记录选择/比较/求助事件。后端决定推荐列表与条件结论，前端只展示。商品详情页读 A 的快照，从而真实表现“分散页面→集中比较”，不假装在线爬取商户页面。

```json
{
  "session_id": "s_001",
  "state_version": 3,
  "action": "recommend",
  "message": "这款满足已确认的内存要求；重量尚无资料可确认。",
  "question": null,
  "recommendations": [{
    "product_key": "us:CATALOG_ID",
    "constraint_checks": [
      {"attribute": "ram_gb", "status": "supported", "evidence_ids": ["e_17"]},
      {"attribute": "weight_kg", "status": "unknown", "evidence_ids": []}
    ]
  }],
  "comparison": [],
  "handoff": null
}
```

此JSON仅演示接口，`CATALOG_ID`与`e_17`是占位符。action 固定为 clarify/recommend/compare/handoff；用户选择商品另记事件，不能让模型代替用户确认购买。旧state_version的异步结果不能覆盖新需求；同一请求重复提交使用request_id去重。

**依赖与联调节奏**

A 第一天提供10商品无标签fixture及属性字典；B同步做BM25与验证器，先消费fixture；C实现工具调用与会话，先消费B的mock返回；D用相同AgentResponse做页面。第二天把A真实快照接入，第三天必须出现第一条真实数据端到端流程。

每天一次15分钟站会、一次固定集成窗口。站会只报已交付、接口变更和阻塞；集成窗口跑三条共享开发案例：条件完整、需要澄清、反馈改条件。代码按模块归属提交，小批合并；共享类型由C维护、评价真值由A维护、部署配置由D维护。接口错误当天解决，功能优化不阻塞主链。

**团队共同验收：可观察的完成标准**

| 场景 | 必须满足 | 主要负责 |
|---|---|---|
| 顾客已给全条件 | 直接查询与比较，不机械要求回答额外问题 | C；D核体验 |
| 关键需求缺失 | 问题能够解释为区分真实候选的必要条件 | C；B供证据 |
| 高分候选违反硬条件 | 不显示为满足；指出具体证据或冲突 | B；A复核 |
| 商品属性缺失 | 显示未知；不会生成一个不存在的数值 | B/D |
| 用户改条件 | 新比较和推荐都符合新状态，无旧结果覆盖 | C/B/D |
| 配件混入主商品 | 能识别并从主推荐中分离，允许独立搭配展示 | B |
| 无可确认匹配 | 解释搜索范围与缺口，给替代协商或交接草稿 | C/D |
| 模型/工具失败 | 有可理解的恢复状态，不伪装成功，不遗留错误结果 | C/D |
| 同时多个会话 | 需求、日志和选择互不混用 | C/D |
| 结果可核验 | 商品ID、数据版本、证据和判断一一对应 | A/B |

每轮设有限工具预算、超时和最多2轮澄清，具体数值由C在资源试跑后固定并记录。内部性能目标可先设“完整推荐P95不超过20秒”，仅作工程目标；实际达不到时先减少候选长文本、缓存固定商品信息和选型模板，实测后再承诺。用户看到明确加载与失败状态，不因追求短延迟隐瞒未完成核验。

**围绕题目的最终结果与演示**

主结果表：ESCI固定候选nDCG@10；冻结会话中的可接受选择成功数、硬条件违反数、未知率、求助数；人工对照下的完成时间与详情页打开数。顾客点击“选择此商品”称为选择完成，不称为购买转化。销售负担用测试中求助与重复说明衡量，真实咨询量/成交率变化需要上线数据。

A组织至少8名可接触的试用者作为目标，每人4项任务，一半使用普通列表/详情、一半使用Agent；任务组与顺序交叉安排，避免同一人先做同一题导致记忆收益。若招募不足，报告实际人数，内部成员试用单列。D记录时间、详情打开、比较、选择、求助；A核验所选商品是否满足任务。未经验证的用户感受不能代替正确率。

演示分工：D开场说明顾客痛点并操作店铺；C演示候选驱动澄清和改条件后的行动；B解释一处规格冲突如何被核验排除；A展示同条件对照结果和数据边界。先准备约3分钟版本用于排练，正式长度依主办方提交入口说明；四人都应能独立走完备用流程。

**风险、降级与工作量控制**

| 风险 | 触发信号 | 谁处理、如何收敛 |
|---|---|---|
| 商品规格不足 | 首日品类门槛未达到 | A在24小时内切换备选单品类；B保留统一属性合同，D不重做页面结构 |
| 模型部署/调用受限 | 第一日无法完成一个工具调用 | C先接可用模型适配器继续；D解决运行环境，模型访问未通时仅内部使用清楚标注的mock |
| 重排太慢 | 候选批次试跑超出交互预算 | B缩短证据文本和批量处理；仍不可用则采用已定义的BM25＋主模型比较路径，并报告真实配置 |
| 完整ESCI评价太慢 | A/B根据100-query试跑外推超出剩余计算预算 | 先在train-derived dev固定500-query迭代；最终目标为完整英文test，预算不足则在看分数前固定1000-query测试子集并明确报告子集规模 |
| 交互策略无稳定收益 | 开发集问更多但成功率未提高 | C降低提问频率，保留更简单的策略；A如实报告，不为体现Agent而强行多问 |
| 队员临时不可用 | 一天内无模块交付 | C接管B的简单检索适配或D接管C的展示兜底；A保数据与评价、D保部署，先暂停全部P1 |
| 无法招募真实试用者 | 试用窗口前无法确定人员 | A组织实际可用人员，披露内部测试身份；不声称证明真实顾客转化或销售工时收益 |

计算预算由A/B用试跑确定，交互用量由C/D记录。截止前优先顺序是：完整可用流程、正确证据与失败处理、可信评价、演示部署，最后才是额外模型或功能。所有降级路径要在技术说明中可见。


**实际采用的策略：一个 Agent、五种能力、一份可用交付物**

用户给出需求后，Agent 根据现有信息选择下一步工具；工具返回数据和验证结果后，再决定继续检索、提问、推荐或转人工。使用单个有状态 Agent 即可，工具作为普通函数实现。

| 能力 | 实际策略 | 产生的业务结果 |
|---|---|---|
| 需求澄清 | 提取商品类型、明确硬要求和软偏好；只问会改变选择的问题 | 少量有效询问，避免反复收集相同信息 |
| 商品搜索 | BM25 主召回，现成 reranker 精排；保留原 query | 快速产生有竞争力的候选 |
| 证据核验 | 查标题、卖点和属性，区分满足、违反、未知 | 排除不符合明确要求的候选，暴露缺失信息 |
| 替代协商 | 无可确认的匹配时说明可选项及偏离，用户允许后再放宽 | 将无结果咨询推进到可接受方案或明确转人工 |
| 选型交付 | 生成 Top-3、条件对比、依据、差异和待确认项 | 顾客可确认的选择结果，及必要的销售交接摘要；下载为P1 |

最终交付物称为“选型单”，不在缺乏真实价格的情况下称为报价单。选型单含需求摘要、商品 ID、满足的条件、证据来源、替代差异与未确认项；转人工时同时带上已问问题，避免客户重复说明。

建议工具接口：`search_catalog`、`inspect_products`、`verify_constraints`、`build_selection_sheet`、`save_handoff_draft`。澄清是面向用户的动作；保存交接草稿即可展示业务闭环。真实对外发送和下单不进入首版范围。

Agent 的自主性体现在分支选择。例如，检索结果出现“品牌正确但型号不兼容”时，先查规格并剔除；高分结果都缺关键字段时，说明无法确认或生成交接草稿；两个可行方案只在用户未表达的偏好上有差别时，再问一个问题。日志显示工具、结果和简短决定依据，无需展示内部推理过程。


**具体技术取舍**

| 项目 | 首版决定 | 原因与升级条件 |
|---|---|---|
| 应用范围 | 一个 SME 工作流程、一个主商品类别、5–8 个可验证属性 | 题目相关性和属性可信度比品类数量更重要 |
| 主模型 | 一个支持结构化工具调用的现成 LLM，优先使用比赛 AWS 账户可访问的 Bedrock 模型 | 型号待账户权限与效果试跑后固定；不预设某型号一定可用 |
| 召回 | BM25 Top-100 | 型号、品牌和规格词重要；优先保证简单基线可靠 |
| 重排 | 冻结的 Qwen3-Reranker-0.6B 对候选逐对评分，保留 Top-20 | 采用已有模型能力；是否部署取决于实测时延与资源 |
| E/S/C/I | 对最终约 10 个候选做结构化判定，并附文本依据 | 是模型预测，不直接当作属性真值；测试标签不进入提示词 |
| 条件验证 | 单位／型号／颜色等能确定的比较用规则；隐含属性由模型提取证据再核验 | 硬反证排除，缺失为 unknown，不能让总分抵消硬条件 |
| 状态更新 | 保存明确条件、偏好、问答、已展示候选及反馈 | 用户改条件后只保留仍有效的要求，重新检索 |
| 训练 | 首版不做专门微调 | 先跑完整业务闭环；仅当评测明确显示排序是主要瓶颈时再考虑小模型训练 |
| dense／RRF | 作为可选对照 | dev 上有稳定收益且资源允许才加入产品路径 |

Qwen3 提供现成 pointwise reranker，但其 yes/no 相关性分数不等于四类 ESCI 概率。[模型论文](https://arxiv.org/html/2506.05176v3)

如果 reranker 在可用机器上过慢，先用 BM25 Top-20 加主 LLM 的候选比较，并记录该替代路径的成本与指标。两条路径不同时建设成复杂路由系统。应用的 Top-100/20 是设计参数；ESCI 给定候选排序实验仍保留其完整候选，不按此截断评价集。

澄清策略固定成可验证规则：先查看候选；只有关键条件不明确且不同答案会改变可选集合时提问。建议最多 2 轮澄清作为初始产品预算，不是赛事限制。达到预算后给出带限制说明的候选或转人工。商品资料缺失应通过查资料或交接解决，不能反复问用户来掩盖数据缺口。

从文献中只保留三项核心启发：ProductAgent 的候选属性统计驱动提问；ESCI 方法的主商品／替代／互补关系区分；AgenticShop 的逐条件证据评价。Rec-R1、FlexRec 的 RL 训练和大规模集成留在研究路线图，不列入提交前依赖。[ProductAgent](https://aclanthology.org/2025.emnlp-industry.25.pdf) · [ESCI 排序方法](https://arxiv.org/pdf/2208.02958) · [AgenticShop](https://arxiv.org/html/2602.12315v1)


**哪些是首版必做，哪些是研究储备**

必须完成的闭环为：需求输入 → 搜索 → 查商品证据 → 核验 → 必要澄清／重新选择 → 选型单或交接。关系分类由现成模型做结构化预测，不宣称获得了已校准四类概率。所有展示事实需有证据，商品 ID 必须真实存在。

领域四分类微调、ESCI 加权 loss、dense/RRF 与强化学习属于研究储备。只有当开发集评价显示主要瓶颈确实来自排序，并且不影响闭环、演示与部署交付时，才从中挑一项做增量实验。冻结测试集不用于选择优化方案。首版不会同时承诺这些优化。


**研究范围与核心判断**

本报告将 Product Selection 定义为：给定用户明确表达或经对话补充的需求，从一个商品集合中选择、排序并解释合适的商品。研究对象包含语义相关性、替代品和互补品判断、属性条件验证及必要的需求澄清。

它与基于浏览、点击和购买历史预测下一个商品的个性化推荐有重叠，但监督信号不同。ESCI 的基本监督单位是 query-product，不是 user-product；没有真实用户历史就不能把实验解释成长期个性化推荐。它也没有网页点击和支付操作轨迹，因此不能直接证明浏览器采购任务的完成能力。

研究证据分成三类：本文的**数据事实**来自固定版本全量扫描；**论文结果**注明来源和实验条件；**实施建议**是据此提出的研究设计，尚不是已经测出的收益。检索覆盖截至 2026-09-11 查阅到的公开工作，不构成对所有未公开工业系统或全部论文的穷尽排名。

建议研究问题定为：**在相同商品候选和评测条件下，语义排序、属性证据验证及按需澄清，分别能带来多少选择质量提升，代价是什么？** 这个问题可以拆成三个可独立检验的假设：

- 现成重排与关系判断是否比纯词法基线更能区分合适商品及替代／互补候选。
- 基于证据的条件验证能降低约束违反，但可能损失推荐覆盖率。
- 根据候选差异决定是否提问，能比固定提问策略取得更好的成功率与交互成本平衡。


**数据集的组织与标签含义**

Amazon ESCI 发布三个相互关联的数据文件。`shopping_queries_dataset_examples.parquet` 存储查询、商品标识、标签、版本和划分；`shopping_queries_dataset_products.parquet` 存储商品文本与品牌颜色等属性；`shopping_queries_dataset_sources.csv` 存储 query 的采样来源。examples 与 products 按 `(product_locale, product_id)` 左连接，再按 `query_id` 连接 sources。[官方数据说明](https://github.com/amazon-science/esci-data)

| 标签 | 任务定义 | 产品选择中的含义 |
|---|---|---|
| Exact，E | 满足查询规格的相关商品 | 主推荐的优先对象；具体标签仍可能有噪声 |
| Substitute，S | 未满足部分需求，但能作为功能替代 | 需要说明差异，并区分用户是否接受该差异 |
| Complement，C | 本身不满足查询，但可配合相关商品使用 | 适合搭配推荐；不应自动成为主商品替代 |
| Irrelevant，I | 不相关，或不满足查询的关键方面 | 应排在相关商品之后 |

E/S/I 的边界取决于某项需求是否关键。例如品牌可能是硬要求，也可能只是用户举例。仅看短 query 往往不能确定，这也是相关性分类和对话澄清需要分开研究的原因。[ESCI 任务与标签定义](https://arxiv.org/pdf/2208.00108)

small 是为排序任务筛选的较难子集，large 包含 small 和额外判断；两者不是两个可以直接拼接的独立数据集。用于排序时按 `small_version=1` 选择，四分类与替代识别可按 `large_version=1` 选择。此次扫描中所有判断均属于 large。small 排除了许多容易的查询，实验结论应限定于这类基准分布。

全量扫描发现三个影响复现的重要问题：

- 论文中的 2,621,738 与当前文件的 2,621,288 不一致；当前 README 内部也存在不同数字。实验以固定文件及 checksum 为准，不能混用论文时期的 public test 和如今发布的 test。
- “最多 40 个候选”不是当前文件的可靠硬限制。small 有 **1,219 个 query 超过 40**；US small train 最大 188，test 最大 95。不要硬编码 40，也不要用文件前 40 行截断评价集。
- large 中 `query_id=79706, query=piano` 同时有 train/test 行。扩大训练时，必须按 query 排除与评测重叠的训练数据。不能认为官方标记已经覆盖所有泄漏问题。

small 的所有 US 训练 query 都有 E，但 US test 有一个 query 没有 E；“至少有一个 Exact”同样不能写成通用假设。全量 `query_id` 有 130,652 个，原始 query 文本有 130,193 种，说明标识符和文本不是同一计数口径。

原始数据来源：[Amazon ESCI 官方仓库](https://github.com/amazon-science/esci-data)。本文给出关键统计及其口径，数据版本和校验值列于文末。


**哪些字段值得处理**

| 字段 | 本次实测 US 商品缺失率 | 用途与处理方式 |
|---|---:|---|
| `product_title` | 0% | 首个词法和语义基线；抽取商品类型、型号、尺寸、兼容对象 |
| `product_bullet_point` | 14.70% | 最优先补充的属性证据：功能、材质、适用对象、包装内容 |
| `product_brand` | 5.95% | 建立别名及标准化表；区分商品品牌和“兼容某品牌” |
| `product_color` | 33.40% | 原值与归一化色系并存；缺失、混色和自定义色名需要 unknown |
| `product_description` | 46.86% | 作为补充证据；清理 HTML，按 query 选片段并限制长度 |
| `query` | — | 检索输入、意图与条件抽取；保留原文及规范化形式 |
| `esci_label` | — | 四分类、同 query 的偏序训练、子类错误分析 |
| `query_id`, `split` | — | 查询级切分和评测分组；不作为模型语义特征 |
| `product_id`, `product_locale` | — | 联合键、去重和语言路由；不能仅按 ASIN join |
| `small_version`, `large_version` | — | 任务范围选择；不输入分类器 |
| `source` | — | 困难样本筛选与分桶分析；是采样来源，不是用户画像 |

缺失口径为 NULL 或去除首尾空白后的空字符串。`product_color` 里还能出现 `Washable`、规格组合等非纯颜色值；有字段不代表有可信的规格事实。商品表没有独立、稳定的价格、库存、配送、类别树、用户画像、尺寸或兼容性字段；部分属性只藏在文本中。

建议首版商品文本顺序：`title → brand → color → bullet points → description 的相关片段`。总预算先设 384–512 tokens，再做字段消融；数字、单位、型号、否定词不能在清洗中删掉。商品证据保存 `{field, raw_value, normalized_value, evidence_span, status}`，`status` 至少包括 supported / contradicted / unknown。


**最值得拿来做实验的条目**

`sources.csv` 有以下现成入口。全量 query 计数：`negations` 6,964、`parse_pattern` 6,083、`nlqec` 169、`behavioral` 3,780、`other` 113,656。它们是采样类别，不应直接当作经过人工验证的 query 类型标签。论文说明 negations 与 parse pattern 主要来自规则筛选，NLQEC 来自自然语言商品查询数据。[原始论文，第 2.1 节](https://arxiv.org/pdf/2206.06588)

缩小到首轮使用的 US small train，仍有 **1,629 个 negations query / 50,303 条判断**、**1,777 个 parse_pattern query / 62,369 条判断**、**69 个 nlqec query / 1,793 条判断**。优先从这三组做开发样本，保留所有其他 query 作为正常分布对照；不要只在困难子集上报总体指标。

| 样本池 | 已有规模／真实例子 | 可做处理 | 还缺什么 |
|---|---|---|---|
| 同 query 有 E 与 S | US small train **18,066 个 query** | E/S 难例、替代识别、成对排序 | S 为什么偏离，以及用户是否接受该偏离 |
| 同 query 有 E 与 C | **5,408 个 query** | 主商品与配件分流，降低配件挤占主推荐的概率 | 具体商品之间的兼容关系 |
| 同 query 四类齐全 | **2,739 个 query** | 诊断集、解释展示、四分类混淆分析 | 少量标签复核 |
| 否定／排除 | `1 in curtain rod black without brackets` | 提取黑色、直径、排除支架；匹配属性证据 | 哪些约束确实是硬约束 |
| 自然语言需求 | `A plain black, warm puffer jacket with a hood and decently sized pockets`，query 5624 | 类型／颜色／帽子／保暖／口袋抽取；软硬区分 | “warm”“decently sized”的可验证标准 |
| 复合电子产品需求 | query 2162 要求 15-inch、轻、较多存储/RAM、HDMI/USB | 数值与接口标准化；缺少阈值时澄清 | “lots of memory”究竟是多少 |

query 5624 的真实候选具有良好的教学价值：E 包含 Orolay 黑色羽绒服 `B00HHOXV7Q`；S 包含橄榄色 Steve Madden 外套 `B0751XL17H`；C 是黑色羽绒服修补贴 `B07YDPQNMY`；I 包含红色儿童摇粒绒外套 `B07NQW2QYF`。这组可展示颜色偏离、配件识别与品类区别。这里只转述原始标签，尚未人工验证所有“保暖、帽子、口袋”条件。

US small train 中，简单规则找到含基本颜色词的 query 1,562 个，含数字 4,395 个，含 for/with/without 4,036 个；1–3 个空格分词的短 query 有 9,642 个。**这些只是重叠的启发式候选池，不是属性抽取模型准确率。**

训练样本中可以看到明确的证据冲突。例如 query 1140：`1/4” black buttons for sewing without holes`，产品 `B07CZWRH6Z` 的标题描述棕色、四孔、2 英寸木纽扣，`product_color=Dark Brown`，却标为 E。query 940 要求 black，部分 E 商品的颜色为 Brushed Nickel。也存在产品类型看上去都不吻合的 E 样本。

这些例子是按颜色等词及四类齐全条件有意挑出的训练难例，**不能用来估计全数据的错误率**。它们证明：训练时可保留官方 E/S/C/I，但评估“硬约束是否满足”时必须另有证据标注；也不能把 E 自动变成“所有约束均满足”。原论文也承认标注噪声与 S/I 边界歧义。[原始论文，第 2.2 节](https://arxiv.org/pdf/2206.06588)

特别注意，ESCI 的 S/C 是 **query-product 关系**。不能从“同一个 query 下有 E 和 C”推出任意 E 商品与任意 C 商品都互相兼容，也不能直接生成经过验证的商品知识图谱。


**数据怎样使用**

保留英文 small 完整测试集用于技术验证，开发时按 query 从 train 划出 dev。实际应用目录从相关品类开始，采用经筛选核验的同类商品固定快照，实际数量由第一天审计确定。ESCI 无可靠类别字段，品类筛选需要规则或模型初筛后人工抽查，不能假定存在现成 category 列。

训练资料中已有 E/S 同时出现、否定需求和复杂属性查询，可以用于设计开发案例。但增加新条件或模拟后续回答时，应重新核验可接受商品；原 ESCI 标签不随需求改写自动有效。ESCI 本身存在标签与属性冲突，不能从 E 标签推导全部硬条件满足。

人工标注工作从 60 个会话开始：20 个用于开发，40 个冻结做机制验证；时间允许扩展到 120 个，其中 40 开发、80 测试。覆盖需求完整、关键属性待澄清、约束冲突、无可确认匹配及反馈改条件。按原 query 分组隔离，评价所有最终展示候选。小样本报告计数和不确定性，不包装成真实商业部署证据。

ESCI 目录和模拟 SME 需求明确注明来源。若有真实 SME 可接洽，优先用少量经授权的目录样本与 2–3 次工作流程访谈验证字段、交接和完成判据。没有企业数据时，先用公开数据证明方法，把“试点待验证”单列；不虚构合作企业、客户采用或转化提升。

**三个评价层不能混在一起**

| 层级 | 输入与真值 | 指标和边界 |
|---|---|---|
| A：给定候选排序 | small 原始 query 的完整已标注候选 | nDCG@10、全深度 nDCG、Exact Recall@K、四类 Macro/Micro F1、S 类二分类 F1 |
| B：全商品库检索 | 同市场 corpus，自行召回 | 对已知 E 计算 Recall@50/100，同时报 judged coverage；未标注商品不等于 I。需要 TREC 或补标才能更充分证明全库收益 |
| C：Agent 选择 | 单独的需求、属性证据、允许澄清答案、多个可接受商品 | Success@1/3、硬约束满足率、unknown 率、推荐覆盖率、平均/P95 澄清轮数、每轮成功曲线、成本与延迟 |

指标定义必须在实验前固定：

- **nDCG@10**：每个 query 先按 `DCG@10 = Σ gain(label_i)/log2(i+1)` 计算，再除以该完整候选集理想排序的 DCG；最后按 query 平均。推荐与排序截断规则需固定。
- **Exact Recall@K**：Top-K 中的 E 数除以该 query 全部已标注 E 数。它与“Top-K 是否至少含一个 E”的 Hit@K 不同。
- **Substitute F1**：把 S 作为正类，其余作为负类，计算正类 precision/recall 的调和平均。四分类 Macro-F1、Micro-F1另报；单标签四分类的 Micro-F1等于 accuracy。
- **硬约束满足率**：在已经做出推荐的案例中，满足全部人工确认硬约束的推荐比例。明确按商品或按会话计算，不混用分母；证据不足不能默认为满足。
- **选择成功率**：在全部评价会话中，于规定轮数和推荐数内给出至少一个经标注可接受商品的会话比例。无可接受商品的场景单独评价正确拒绝或说明能力。
- **覆盖率与 unknown 率**：同时报告是否给出推荐，以及推荐中有多少条件无法验证，防止系统靠大量弃答提高满足率。
- **交互成本**：平均澄清轮数以全部会话为分母，并报告成功会话的条件均值、P95、每轮累计成功率和延迟。

开放检索的未标注问题尤其重要：ESCI 只为每个 query 的部分商品给出判断。新检索器找到了原来未标注但实际合适的商品，如果把它一律计为 I，会系统性低估收益。若暂时采用这种约定，应明确披露，并补报已判定覆盖率；更充分的端到端检索比较应对各系统候选进行池化补标或使用 TREC 的评价集。[TREC 产品搜索评测](https://arxiv.org/html/2608.17138v1)

US small train 标签分布：E 181,819 (**43.33%**)，S 147,628 (**35.18%**)，C 19,090 (**4.55%**)，I 71,116 (**16.95%**)。只报 Micro-F1 容易忽视 C，故保留每类 F1 和混淆矩阵。Exact Recall 的分母是该 query 已标注 E 的数量；E=0 的 query 排除于该指标均值并另报数量。nDCG 的 gain 直接使用 `{E:1,S:0.1,C:0.01,I:0}`，不要再作 `2^gain-1`。全零 IDCG 需要明确定义并统计。

代码审阅还发现官方历史脚本不一致：训练映射 S=0.1/C=0.01，但 `prepare_trec_eval_files.py` 编码 S=2/C=3，启动脚本又指定 2→0.01、3→0.1，组合起来交换了 S/C。建议按论文的标签 gain 实现，并编写微型手算用例；如复现历史脚本，应另外命名协议，而不是假定 README 的 0.83 可直接比较。[训练脚本](https://github.com/amazon-science/esci-data/blob/7916cdf6ab75a462e77f20ab40428a10923998d5/ranking/train.py) · [qrels 脚本](https://github.com/amazon-science/esci-data/blob/7916cdf6ab75a462e77f20ab40428a10923998d5/ranking/prepare_trec_eval_files.py) · [评测命令](https://github.com/amazon-science/esci-data/blob/7916cdf6ab75a462e77f20ab40428a10923998d5/ranking/launch-predictions-task1.sh)

模型选择只看 train 内按 query 划出的 dev；建议按规范化 query 文本一起分组，从 US train 留出约 10%。不要随机拆 query-product 行。扩大到 large 时排除 dev/test 的 query；预训练模型使用过 ESCI 与否通常不能完全审计，应在模型卡中披露这一不确定性。test 只用于最终固定方案评测，按 query bootstrap 报差值置信区间。

人工会话评价统一采用前述 60→120 会话规模，不把原研究建议的 300 条列为提交依赖。人工确认硬／软条件、证据、允许澄清答案及可接受商品；按原 query 分开开发和测试，标注员不看模型排序。新增条件需要新真值，不能沿用原 ESCI 标签。模拟器只读取需求卡，不读取模型答案或排序分数。

对于实际展示的候选，检查全部推荐项的约束与证据；如果只标注了一个小候选池，就只报告该范围的选择质量，不能推广到全商品库。无匹配样本也应区分“候选内没有可接受项”和“全库确定没有”。

ESCI 技术评价保留原 query 的完整候选；应用中的 Top-100/20/10 不改变这个协议。Substitute F1 等四分类指标要在明确报告的已判定样本集合上计算；若仅评价 Top-10，必须注明是条件化子集结果，不能称为全量 Task 2/3 成绩。排序主指标与关系分类指标允许采用不同评价范围，但应分别写清分母与样本选择。

首版消融只保留关键问题：重排是否改善排序、证据核验是否降低违反率、候选驱动澄清是否优于固定询问。每次只改一个组件，并记录退步与失败类型；可选模型实验不挤占这三项验证。


**用四类证据支持比赛叙事**

| 证据 | 采用的指标 | 比较方式 |
|---|---|---|
| 技术质量 | nDCG@10、Exact Recall@K、Substitute F1 | 同一 ESCI 候选：BM25 与实际采用的重排系统 |
| 选择可靠性 | 全条件满足率、unknown 率、覆盖率、会话成功数 | 同目录、同需求卡：单次推荐与完整 Agent |
| 交互价值 | 成功率随轮数变化、平均澄清次数、条件变化后的恢复率 | 不澄清、固定 1 问、候选驱动澄清 |
| SME 工作价值 | 完成选型单的人工操作时间、漏掉的明确条件、人工交接后的重复提问数 | 相同任务的人工流程与 Agent 辅助流程，控制任务难度和顺序 |

需要两个强对照：BM25 技术基线，以及能访问相同商品资料的单次 LLM 推荐基线。不能只与完全看不到目录的聊天模型比较，否则无法证明 Agent 决策本身的增益。

有真实操作者时，做小规模配对试验，并区分人类操作时间与系统等待时间。月节省工时可按“每次节省分钟 × 每月适用咨询量 / 60”估算，但其中未实测的输入必须标记为假设。没有线上业务数据时，不承诺销售转化率、退货率或收入增长。

内部验收目标建议为：所有展示商品 ID 都在目录中；每项事实性理由都能找到证据或被标为未知；已确认的硬冲突不进入满足列表；三类关键流程可重放。质量提升幅度、延迟与成本以实测为准，目标不是已实现结果。


**演示应该让评委看到什么**

建议准备一个主场景、一个失败恢复场景和一个未预先固定答案的交互入口。以下是设计脚本，具体商品与属性必须提前用实际目录核验，不能在演示时编造。

| 环节 | 屏幕上发生的事 | 证明的能力 |
|---|---|---|
| 模糊咨询 | 用户描述用途，Agent 搜索后发现关键规格未确定 | 识别信息缺口，并用候选证据决定是否问 |
| 定向澄清 | 只问能影响选择的型号、用途或必备功能 | 提问有可说明的价值 |
| 排除陷阱候选 | 检索高分商品因明确规格不符被排除 | 排名高不等于满足需求 |
| 需求改变 | 用户改变偏好或允许一个明确替代条件 | 更新需求并重新选择，不沿用失效条件 |
| 生成结果 | Top-3 对比、明确的选择结果；P1可加下载 | 顾客能够理解差异并完成选择 |
| 无法确认 | 生成含缺失字段的交接草稿 | 遇到边界时仍有可用交付 |

主界面保留三个区域：需求与对话、候选及条件对比、可展开的工具执行记录。用户层显示具体条件和差异，ESCI 字母标签放到技术评测视图。用前后对照说明某个候选为何被替换，不堆积工具动画。

演示长度与视频格式待正式提交说明确定。可以先准备一个约 3 分钟的精简版本，作为内部排练目标而非官方时长要求；另备网络故障时的明确标注录屏和可重放日志，不将缓存轨迹冒充实时执行。

对原型必要的控制包括：商品描述作为数据处理而非指令；工具参数按 schema 校验；返回 ID 限定在目录；推理日志不含凭据；持久状态按会话隔离；保存与发送交接分别处理。这些控制直接服务于演示可靠性和业务交付，不增加无关平台建设。
