# Description module integration

The workflow imports the sibling `description_module` through
`shopping_agent/description_adapter.py`. All integration code lives in
`agentic_workflow`; neither `description_module` nor `search_tool` is edited.
Keep both sibling packages alongside this folder when running the application.

## Run

For a ten-turn replay of deferred comparison preferences, a recap, price-question
follow-ups, an item correction, a polite clarification reply, Undo, and finalization:

```sh
python -B -m agentic_workflow.showcase --backend demo --scenario clarification --output agentic_workflow/showcase_clarification
```

Open `agentic_workflow/showcase_clarification/index.html`. The products are
synthetic; the responses, saved requirements, comparison, and audit come from
the actual local workflow. Eight English-submission tests and 67 browser checks
passed after adding this replay. No live model quality claim is made.

Open `agentic_workflow/showcase_revisions/index.html`. The replay uses synthetic

```sh
python -B -m agentic_workflow --demo
```

Open http://127.0.0.1:8000 and try:

1. `I need a blue cotton dress under $50.`
2. `Compare #1 and #2.`
3. `I prefer pockets.`
4. `Compare #1 and #2.`
5. `Finalize my selection.`

You can also use **Compare saved options** beside the shortlist, or type
`Compare my saved options`. This uses the saved product IDs and current
preferences even after a later search has changed the displayed results.
The button is disabled while a message is being sent or an unfinished draft
is present, and becomes available again after a failed request.

An unavailable item number, such as `Compare #99` or `Compare #2 and #99`,
asks for a correction before changing the saved selection or running the
description model. The shopper can answer with just `#1 and #2`. A new
shopping request abandons that short-lived reference clarification.

Explicit comparison uses exactly the named products, in the requested order:
`Compare #3 and #2` does not include another saved item. If the shortlist is
full, additional displayed items can still be compared without displacing saved
products. The response identifies unsaved comparison items. `Compare my saved
options`, finalization, and export continue to use the saved shortlist.
Requests for more than three items ask which smaller group to compare before
changing the shortlist or calling the model.

Comparison handoffs expose `comparison_scope` (`requested_products` or
`saved_options`) and `saved_asins`. Their `selected_products` and comparison
matrix contain only the products in that scope. Caching includes those exact
product IDs and their order, so changing the compared group refreshes the result.

Natural requests such as "What's the difference between #2 and #1?" use the
same comparison path. "How do my saved options differ?" uses saved IDs, while
"Compare these two" requires exactly two displayed products or asks for ranks.
If that clarification accompanies a preference update, the update remains
unapplied until valid ranks arrive. A recap distinguishes it from saved
preferences; an identifiable product-detail question or contextual detail
follow-up preserves it, and
"Never mind" cancels it. "I'm not sure yet" keeps it pending without applying
preferences or searching again, and offers the same cancellation option.
A new request discards it. Successful resolution
uses the original displayed references and supports Undo for the preference.

A preference update and comparison can share one message: `I prefer cotton,
compare my saved options` or `Compare #2 and #1, I prefer cotton`. References
are bound to the previous display before search refreshes. The description
module receives the updated requirements, and its usage is included in that
same turn. Undo restores the requirement edit. This currently supports
separately phrased updates within the same product category; a category switch
or conflicting multi-action request still needs separate clarification.

Omit `--demo` to use the actual search index. Its current product records do
not include prices or full descriptions, so start with `I need a blue dress`
instead of requiring a verified price cap.

The default mode uses the module's `offline_preview`: direct catalog facts,
explicit unknowns, and no model-generated personalized advice. For the full
three-stage pipeline, use the existing configured model provider:

```sh
python -B -m agentic_workflow --demo --model-provider local --model YOUR_MODEL --model-base-url http://127.0.0.1:11434/v1
```

`--model-provider deepseek` uses the existing `DEEPSEEK_API_KEY` environment
variable. The same provider handles optional requirement assistance and the
description pipeline. Provider settings and cloud disclosure stay consistent.
This integration adds no credentials or automatic external model calls.

## Data flow

In offline mode, the workflow adapter also copies unambiguous labeled metadata
such as Material, Fabric Type, Size, and Care into the comparison table. Values
retain the exact listing wording and source field. Conflicting aliases,
placeholders, and non-finite numbers remain unknown. Fabric type is not treated
as proof of composition or purity. This fallback adds no personalized claims
or model calls; provenance records the fields supplied by the workflow.

Search and ranking → displayed results → user selects up to three products →
selection handoff → `DescriptionComparison.compare()` → comparison panel and
JSON export.

The handoff carries bounded titles, descriptions, bullets, details, prices and
ratings together with current hard requirements, soft preferences and exclusions.
The search adapter preserves description fields when supplied; it does not
invent full descriptions or fetch them from another source.

The module owns attribute extraction, objective comparison, personalized advice,
and source-quote checks. Its complete `description-comparison.v1` result appears
under `handoff.comparison_assist` in chat, `/api/handoff`, audit receipts and exports.
Comparison preserves the selection order and does not rerank search results.

The page separates listed facts from personalized advice, labels inferences,
shows missing cells as Unknown, and groups wholly unavailable dimensions in an
expandable section. Quotes are available through “View source.” The terminal
demo and generated standalone showcase also include the module's output.

Shared explicit values are grouped under **Shared details** so distinguishing
values are easier to scan. A partially missing row or an inferred value stays
in the main table. Product names remain visible even if every supplied value is
shared; matching listed attributes do not imply identical products or a winner.
This display behavior follows
[Baymard's comparison-scanning research](https://baymard.com/blog/user-friendly-comparison-tools).
All 50 browser checks and four English-demo checks passed for the presentation
update, and the regenerated showcase completed its four-turn audit.

Rows relevant to the shopper's requirements and exclusions now come before
soft preferences and other attributes. Requested rows stay visible even when
their values are shared or unknown: a stated budget keeps the price row in
view, and a fabric preference keeps material/composition in view. This is
presentation order only; the objective values and product ranking do not change.
The priority display passed 53 browser checks and five English showcase tests.

Repeated comparison, finalization and export reuse a session cache. Changed
requirements, selected products, supplied catalog facts, or model identity
invalidate it. Cached calls report zero additional tokens. Failed model stages
retain available results with `partial` status; the shopper can still finalize.

Partial comparisons can be retried explicitly. Repeating a comparison bypasses
its partial cache, and `Try again` retries the immediately preceding failed
comparison with the same product references. A suggested reply exposes that
option. Export and finalization continue to reuse the available partial result;
they do not silently trigger another model attempt. Successful comparisons
still use the normal cache. Retry usage is recorded on the retry turn.

Retries retain the failed comparison's product IDs, including after a combined
preference-and-comparison turn refreshes the result page. They do not resolve
old item numbers against that new page or add items to the shortlist again.
The same retry remains available if another model attempt is partial. Each
attempt requires an explicit shopper reply; there is no automatic retry loop.

## Verification

### Product-question continuity

"Tell me more about it" uses the single displayed item, or the item already
being discussed. Otherwise it asks which product, offers up to three rank
buttons and "Never mind," and accepts replies such as "the second one."
A preference recap preserves the question. Dismissal leaves results,
requirements, and saved selections unchanged.

Standalone hesitation, such as "I'm not sure yet" or "Let me think," also
preserves a pending detail question. No search or automatic selection runs;
the item-number replies and "Never mind" remain available. The shopper can
resume with "the second one," cancel, or change the request. A message such
as "I'm not sure yet, change to blue" still reaches requirement planning.
Comparison-reference clarification uses the same bounded hesitation detector.

This adapts the context-sensitive recovery principle in
[Google's conversation-design guidance](https://developers.google.com/assistant/conversation-design/errors):
avoid repeatedly demanding an answer and provide a usable way forward.
The guidance concerns voice interactions; this text interface keeps the session
open and offers an explicit escape rather than automatically ending it.
The detector handles the tested standalone phrases, not arbitrary uncertainty
or unrestricted language understanding.

Supported detail topics include material, fit, catalog price, overview, and
care. "What about the first one?" carries the last answered topic; an explicit
topic overrides it. Separately phrased questions and requirement changes can
share a turn, with references bound to the old result list before retrieval.
New searches discard the carried topic. Care answers quote supplied instructions,
flag common machine-washing conflicts, and never infer washability from fabric.
This is bounded catalog question answering, not unrestricted product expertise.

Item-reference corrections such as "Sorry, I meant the second one," "Actually,
#2," or "No, #2" reuse the pending or last answered detail topic. They do not
select a product or repeat retrieval. An unavailable rank asks for a valid item
without answering about the old one. The same correction can accompany a
separate requirement change; its reference is bound before refreshing results,
and Undo restores the requirement change. Without a known detail topic, this
shortcut does not guess one. Negated or multiple references are not silently
treated as a single correction.

This follows [Microsoft HAX's efficient-correction principle](https://www.microsoft.com/en-us/haxtoolkit/guideline/support-efficient-correction/):
let people refine the relevant part without rebuilding the whole request.
